# Custodian: context

Working memory for whoever changes this plugin. Read it first, update it in the same pass whenever a change makes it stale, and add a dated line to the change log at the bottom. Every name in this file is invented, because the release check refuses real ones.

## What this is

A Claude Code plugin in three parts.

- **The audit.** `lib/run.sh` discovers every CLAUDE.md, rule file, skill, agent, custom command and imported file across the owner's global, group and repo tiers, has a headless Claude Code agent judge whether each sits in the right tier, and replaces a report. It changes nothing it audits.
- **The dashboard.** `lib/dashboard.sh` turns that report into one self-contained page on the owner's disk. The page cannot write, so `lib/ack.sh` saves what the page prepares.
- **Freshness.** `lib/status.sh` measures what has drifted on disk since the audit and says whether the report is stale. `hooks/remind.sh` tells the owner, once a day at most, when a session starts.

`bin/custodian` is the one command in front of all of it. `skills/` and `hooks/` are what the plugin adds to Claude Code: four user-invoked skills that call that command, and one session-start hook.

## Where the owner's data lives

Everything that belongs to the owner sits in one data folder, `~/.custodian` unless `CUSTODIAN_HOME` says otherwise: the config, the examples, the report and its baseline, the status of the last drift check, the saved acknowledgements, the offers turned down at setup, the generated page, failure evidence, the hook's stamps and a pointer to the plugin's install path. Nothing of theirs is ever inside the plugin, because Claude Code replaces a plugin's folder on every update.

It is deliberately not Claude Code's own per-plugin data folder. That one is only defined inside plugin components, sits under one config directory, and may not survive an uninstall. The owner's data has to be reachable from a plain terminal and be the same whichever account is active.

## The rules everything hangs on

- **Reach decides how an item is judged.** An item's tier is the broadest place it is loaded from, not where its bytes live. A group's skill symlinked into the global skills folder is `global`, so group detail in it is a leak.
- **Home decides who reads it, and where the dashboard files it.** An item is read in the batch of the root that contains its canonical file, under that group's own Claude account. The report carries `home` as a structured field, because an id cannot say whether a file lives at group level or inside a repo.
- **The runner owns facts, the agent owns judgement.** Anything the runner can compute is never asked of the model, and anything the model returns that can be checked is checked.
- **One definition of stale.** Drift of any kind, changed examples, changed roots or exclusions, a changed model or account, a changed prompt, or older than the backstop. The hook, the status command and the page all read it from the status file or the baseline. None of them re-derives it.
- **The trigger stays human.** Nothing runs on a schedule and nothing calls the model by itself. The tool says when and why, and the owner types the command.
- **Report text stays out of conversations.** The skills relay counts, ids and paths. The report mixes groups and a conversation runs under one account, so the text is for the dashboard only.

## What the config's words mean

- `global` is the user-level Claude folder, loaded by every session.
- `client` means a group: a folder holding several repos that work as one thing. A paying client is a group, and so is a multi-repo product of the owner's own. A group is the leak boundary.
- A **config folder** is a folder Claude Code uses as one account's configuration: a `global` root, or a root whose canonical path `slots` or `default_slot` names. Every other root is a group folder or a repo.
- `slots` names the config folder of a group that has an account of its own. `default_slot` names the config folder of the owner's own login when that is not `~/.claude`, and every batch without a slot of its own runs under it. Not a reserved scope such as `personal`, because that is a likely name for a group.
- `project` means one repo. Inside a group it takes the group's scope. A standalone repo has no scope. A `project` glob names a file or a folder each repo holds, and the repo is the folder holding the match, or the folder above it when the match sits in `.claude/`. The two shapes every document shows are `…/CLAUDE.md` and `…/.claude`, which between them find a repo that keeps anything Claude Code loads. A glob that names a CLAUDE.md passes over a repo that keeps only rule files, skills, agents or commands, and nothing can say so. A glob on `.git` would make a root of every checkout, and the hook's check grows with the roots.

## What the freshness words mean

- A **fingerprint** is the SHA-256 of a judged file, taken from the staged copy, so it describes exactly what was judged.
- A **found path** is a path at which the expansion finds a context file, before links are resolved. One item can have several.
- The **baseline** is what the last successful audit saw: every found path from the raw expansion with what it resolved to (the file's identity, size and modification time, and the fingerprint of the judged file it led to), the same for the examples, a copy of the config's roots and exclusions, and how the report was judged: the model and the accounts from the config, and a fingerprint of the prompt and the schema. It is written beside the config, before the report moves into place, and what the paths resolved to is recorded before anything is staged.
- **Drift** has four kinds: changed, new, gone and relinked. Relinked is the same file loaded from different places, which is how a group's skill becomes global.
- The **full check** runs discovery and hashes everything. It takes seconds, so it runs for `status`, `dashboard` and `audit --if-stale` and never at session start. The **quick check** re-expands the patterns, stats every found path in one call, following links, and hashes only the suspects. That is how it sees a link pointed at another file, which adds and removes no path. It may over-report and must never under-report, and whatever the full check rejects it stops counting. One blind spot is accepted: a file replaced by one of the same identity, size and modification time.

## Decisions not to re-litigate

- `--allowedTools` alone is not read-only. Verified: the session kept Bash, Edit, Write and every MCP tool. Each flag in `invoke_batch` closes one door and the smoke suite asserts the whole set.
- Every run asserts its own tool surface from the stream's `init` event, and requires the fields it checks to be present. A Claude Code update that widens the surface or drops a field fails the run with exit 3. That failure is the design working.
- The judge never inherits `CLAUDE_CODE_PLUGIN_DIRS`, and the same `init` event must list no plugin but Claude Code's own. Safe mode lists a plugin named by that variable without running its hooks, seen on 2.1.296, so the list is what a run can check. Where an organisation's managed plugins are listed in safe mode the run fails, and that could not be tested.
- `CLAUDE_CONFIG_DIR` is never inherited. It is set byte for byte for a batch that has a slot, its own or the default one, and unset otherwise, because Claude Code keys the stored login on a hash of the exact string.
- The judge runs on a Claude subscription and on nothing else, which three things hold. Its session is given a named list of variables, with any `LC_*` and `XDG_*`, and no other: `SEALED_KEEP` in `lib/seal.sh` holds what a process needs, the network path with its proxy and certificate settings, and the output limit. Before anything is sent, each account a batch would run under is asked `claude auth status` in that same environment and must answer a logged-in `claude.ai` login with Anthropic as the provider. And the `init` event must report `apiKeySource` as `none`. The first is a list of what passes and not of what is left out, because no list of names to leave out can be whole. Two reviews each found more: the 2.1.296 build reads dozens of variables its documentation does not list, for a credential, an endpoint or a trace, some named for Claude Code and some not. A changed endpoint is the one thing neither later check can see. The price is plain to see where the other was not: a variable the owner's network needs and the list lacks makes a batch fail to connect, and is then added to the list. The second sees a token or a provider, which the third does not report; the third sees what the session really used.
- `claude auth status` reads the account's settings and a session in safe mode does not. A key kept in settings therefore refuses the run, though the judge would not have used it: seen on 2.1.296, where a key in the settings' `env` and an `apiKeyHelper` both showed in the status and neither in a sealed session's `init` event. A run that goes ahead on a guess is worse than one that says what it found.
- The runner repeats nothing `claude auth status` says but the kind of login, the provider and where a key came from. The answer also holds an address and an organisation, and the stand-in's answer carries marked ones so a case can look for them.
- A group with an account of its own is sent nothing its sessions do not load and nothing that names another group. Its batch has no reference files, knows no scope but its own and no standalone repo, and where `linked_from`, `imported_by` or `above` would name a place outside its own roots and its own files, or a file's `scope` is another group's, the batch is told `outside this group`. The report keeps every path, because it is assembled from the runner's manifest and never from what was sent. A session under a config folder of its own loads that folder's CLAUDE.md and rule files and nothing from `~/.claude`, seen on 2.1.296 through the `InstructionsLoaded` hook.
- Claude Code older than 2.1.295 is refused, by the runner before anything is sent, by the seal from the `init` event's own version, and by `doctor`. That release fixed `--tools` and `--restricted` not applying to built-in tools that register after launch, and a tool that registers late is one the `init` event never lists. The floor is `CLAUDE_CODE_FLOOR` in `lib/claude-flags.sh`.
- A session that ends in an error is reported in Claude Code's own first line, cut at 200 characters. That text is Claude Code's, never the model's and never a file's. Claude Code exits 1 on an error result, so the runner reads the result before it reports the status. A usage limit is known by status 429 or by its words; a real one was never seen, so whatever Claude Code says is quoted.
- The report's `usage` is what Claude Code said the sessions used: tokens in, with cache reads and writes, tokens out, seconds, and the figure it gives as cost. That figure is kept as `api_equivalent_usd`, because a subscription is not charged by the run. When any batch lacks a figure the total is null, never a part. `plugin_version` says which version wrote the report.
- The runner deletes a `failed` folder only when it is its own: one that holds the `reason.txt` it writes first, or an empty one it can read. A folder it cannot read is not taken for an empty one. With `output` set, the folder beside the report may be the owner's, so beside a foreign one no evidence is kept and the message says so.
- A lock is live only while its pid belongs to the run that wrote it. The run records the process's start time beside the pid, since a pid alone is handed to whatever starts next. A lock with a pid and no start time, as older versions wrote, is still believed while the pid is alive.
- The examples need a group example only when the config has a group. A config that audits the user-level folder alone would otherwise be asked for a skill tied to a group it does not have.
- `custodian detect` reads the disk and proposes; the setup skill puts what it finds to the owner. A finding is an offer with a key, a glob as much as a group, and one the owner turns down is recorded in `setup.json` and not made again. It writes nothing else, and never the config: the skill shows the config and writes it once the owner agrees. The starter config `init` writes is nobody's choice, so it is recognised before it is tried, since it finds nothing where the default folder holds no context yet, and over it the proposal is made whole, with the global root where the login is. Beside a config of the owner's own it only adds, and one that finds nothing yet is still well formed.
- Detection reads names and never content. Claude Code keeps one folder per working folder in a config folder's `projects`, named after the path with every other character turned into a dash, so a name is tried against the disk to learn where sessions ran. A remote's owner is read from `.git/config` to compare with its neighbours' and is never printed. A context-central estate is read from its `estate.json` with `jq`: the other plugin is never called and need not be installed.
- A group is offered on a sign and never on shape: a CLAUDE.md or a `.claude` folder of its own, a context-central estate that holds several repos, or an account other than the default whose every session below the home folder ran there. A folder of unrelated repos has none of these and stays a folder of standalone repos. A single repo that one account alone works in is offered as a group of one, since `slots` can name an account only for a group.
- Session evidence is thin. On one real machine most session folders named temp folders, and a third of those below the home folder no longer existed, so detection says only what the folders still on disk show.
- The version lives in `plugin.json` alone. The marketplace entry carries none, and the release check fails when it does, or when the changelog's newest section names another version. With the number in two places a release can ship one and announce the other.
- The plugin installs as `custodian@azamkhanuk`, from a marketplace that is a repository of its own, `azamkhanuk/claude-plugins`. It lists each of its author's plugins by the plugin's own GitHub address, so the install id carries the author's name, as the owner ruled on 2026-10-13. Claude Code keeps one marketplace to a name: a second one added under a name already registered takes the first one's place, and whatever was installed from the first stops loading. Seen on 2.1.296. So this repository's own marketplace is `custodian-dev`, for installing from a clone, and never carries the name the plugin installs under. For the same reason removing the plugin is never given as removing the marketplace, which other plugins install from.
- The workflows stay off while the repository is private, unless someone starts one by hand. The suites run only on macOS, and a private repository pays ten times for macOS minutes.
- The pre-push hook is for a clone whose whole history may be published, as this repository's is: link `scripts/pre-push` as `.git/hooks/pre-push`. The plugin was first developed in a private history that named things, so this one began as a single commit of that tree, made by `scripts/release-export.sh`.
- The plugin is developed in this repository, in the open. A pull request raises the version and adds the changelog's section, and the release workflow tags and publishes once the checks pass on `main`. The release check runs before any push, through the pre-push hook.
- The audit's sessions run with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, so Claude Code's own analytics and error reports are off for them. A session in safe mode ignores a telemetry switch kept in the account's settings and honours one in its environment: seen on 2.1.296, where the `init` event's `analytics_disabled` stayed false for the first and turned true for the second. The seal fails a session whose `init` event says analytics are on, and says nothing where the event has no such field, since that field is not known before 2.1.296.
- Claude Code is never shown a folder it has not used as a config folder. Given one in `CLAUDE_CONFIG_DIR`, it sets a config up there and runs its first-start migrations over whatever `settings.json` lies in it. Seen on 2.1.296: naming the default folder made a `.claude.json` inside it and rewrote its settings file, and on a copy the same step turned a `model` of `opus` into `opus[1m]`. So a slot with no `.claude.json` in it is said to hold no login without Claude Code being asked, in the audit, in `doctor` and in `detect`. And `default_slot` may not name `~/.claude`: Claude Code keeps that folder's login under no name and does not find it once the folder is named.
- The runner knows the block context-central writes into a hub by its two marks. Those, and the `estate.json` that `detect` reads, are all Custodian knows of the other plugin. The lines between them are a fact of the manifest, `generated`, and a finding there that calls the text too generic is dropped once its quote has been checked: a `warn` whose suggested tier is broader than the file's own. A leak inside the block stays, and so does text there that is too specific. The real model called that block too generic in one live run of two on 2026-10-13, so the prompt alone does not hold it.
- The seal is read twice. `await_seal` polls the stream file and applies the `init` rules as soon as that event is there, and a break stops the session before the batch is judged. The whole stream is checked again at the end. It polls the file and does not read a pipe, so bash never sits between the model's answer and the disk.
- The agent reads staged copies inside a fenced folder, and a batch's copies are deleted as soon as its response has been checked.
- A quote that matches no line of the file fails the whole run.
- The exit code says whether the audit ran, never what it found.
- The dashboard is a generated file with no server. Its policy allows only its own hashed script and style and forbids every connection. Report text is escaped, inserted last and rendered as text.
- The page uses no browser storage. Filters live in the page address, and saves go through `custodian ack`.
- An acknowledgement's key hashes the item id, the verdict and the normalised text. Line numbers are left out so edits elsewhere do not orphan a decision, and the verdict is included so a warning that becomes a leak comes back.
- A partly accepted file's advice follows the entries still open, so accepting a leak never leaves its "belongs with" sentence behind.
- The view model decides everything the page shows, including each item's band and top-level node. The page renders and filters; it never re-derives.
- `custodian ack` slurps its payload and requires exactly one document, because `jq -e` alone reports on the last one and a second could ride in behind a bad first.
- The release check fails closed. It stops when it cannot read names from the config, when the repository has no commits, or when git cannot search. A name of five letters or more matches anywhere in any case; a shorter one only where it is not part of a longer word, or a three-letter scope would turn up inside ordinary words. A root's path always matches and cannot be ignored. It reports how many names were ignored, never which.
- An import checks everything before writing anything. It replaces only a starter config or a stub that nobody has edited, and refuses otherwise.
- `editor_url` must be an editor's own scheme and contain `{path}`. Web addresses and script schemes are refused in the config and again in the page.
- Skills call `"${CLAUDE_PLUGIN_ROOT}/bin/custodian"` by absolute path. A bare `custodian` could resolve to the owner's terminal launcher, and then the install pointer would never move to a new version.
- The plugin ships exactly one hook, at session start, and no servers, agents, monitors or settings. A packaging case states which hook, so that a second can never arrive unnoticed.
- The hook speaks through one JSON document whose only key is `systemMessage`. Claude Code shows that to the person and not to the model. Plain stdout and `additionalContext` both reach the model, so they are never used. All three were probed.
- The reminder's line holds counts, ages and the plugin's own commands. It never names a scope, an id or a path, because the session it lands in may run under any account. The age is given once: a second reason says "too".
- The hook always exits 0 and records its own errors for doctor. A broken reminder must never decorate every session with an error.
- The hook's early path runs nothing but `date`, and nothing at all before it has ruled out the audit's mark, an unattended session and any event that is not a start. It claims the hour before it reads the config and the day before speaking, each by creating a stamp that must not exist, so several sessions restored together produce one check and one line, and a check that is killed is not retried for an hour. It asks which system it is on only after that claim, so the early path still starts nothing else.
- Only an explicit `CLAUDE_CODE_SESSION_ATTENDED=0` counts as unattended. The variable is undocumented, so if it disappears the worst case is a reminder spent on a headless session, not a reminder that never appears again.
- How a report was judged is part of what makes it stale. The hook sees a changed model or account, because both are in the config its one `jq` already reads, and it says so in a sentence of its own. It does not see a changed prompt: that would cost it a hash, and a plugin update is not the owner's drift. The full check sees both, as the reasons `judge` and `prompt`. A baseline from before these were recorded says nothing of how its report was judged, so nothing is called stale on its account.
- With no baseline beside the report the hook checks nothing on disk, and says only the audit's age and the leaks still open, which the report and the saves decide. It used to repeat the drift counts of the last full check, however old that was.
- The hook never opens the report. It believes a status only when it names the same report as the baseline beside it. The rest is kept true elsewhere: a successful audit replaces the baseline and removes the old status, an import removes both, and the full check removes a baseline that belongs to another report.
- `custodian status` takes `--json` and nothing else. The modes other commands use to record a fresh status or to recount are not reachable from it, because one of them would stamp a drifted estate as fresh.
- Every script takes the current time from `date` and never from `jq`, so that one stand-in moves the clock for every test.
- Drift annotates and never recounts. Verdicts and keys come from the report alone. The page's counts, the headline's and the tree's alike, count what the ledger shows, and the ledger lists a file that has gone apart, so such a file is counted nowhere: a file that is not there cannot still leak. A file that changed or is loaded from somewhere new is marked and still counted. The status leaves gone files out of its open leaks for the same reason.
- Every reader asks a file's `schema_version` before it reads it: the dashboard, the status and the save for the report and the saved acknowledgements, the full check for the baseline, and the hook for the baseline and the status inside the one `jq` it already ran. A file of another version is refused in one sentence and never guessed at. The full check does not read such a baseline: it sets it aside whole as `baseline.unread.json`, says so in one sentence and measures drift without it. Left in place, the hook would give up on it at every check, and only an audit would end that. Saved acknowledgements with no version are read as version 1, which is what the first saves wrote.
- The page's terminal command is `ack_command` from the view model: the pointer file inside a command substitution, so it works without the launcher and across plugin updates. A data folder that is not the default is named in the command.
- `status` exits 0 whether or not the report is stale, because an exit code says whether the command worked and never what it found.
- One kind of test seam: a command line, a fixture folder, a fake `claude` first on `PATH`. No test framework, nothing tested in a browser. Two checks run the real `claude` and are opt-in: the live taste check, which spends usage, and the loading check, which does not.
- Stock macOS only: bash 3.2, `jq`, `realpath`, `shasum`, `xxd`, `base64`, plus `check-jsonschema` from Homebrew. No GNU coreutils. Anywhere else every command but `doctor` and `version` refuses with exit 2 before it writes anything, `doctor` says that one line and stops, and the hook is silent. The one question is `uname`, so a stand-in can answer it in a case.
- Batches run one after another and nothing retries.
- A rule file is looked for by the type of root: `rules` in a config folder, `.claude/rules` in every other root. A group folder's or a repo's own top-level `rules` folder is never read, because Claude Code does not load it and it may hold anything.
- A config's glob may escape a glob character, so that a bracket in a folder's own name matches itself, and `detect` offers such a place that way. `config_roots` undoes the doubling `@tsv` gives a backslash, which until then made any backslash in a root or a glob match nothing.
- A rules folder is walked by the shell's own globbing, eight folders deep. The quick check therefore starts no process per root, and a circular link ends at the cap. A name that starts with a dot is not found.
- A rule file with `paths` in its frontmatter is judged like any other. `paths` changes when it loads and never who can load it, and the runner does not read frontmatter.
- The kinds judged line by line are named once, as `by_line` in `lib/jq-defs.sh`. The runner's shape check, the reference files, the entries and the dashboard's view all ask it.
- An item's kind is the kind it has where it lives: that of the first hit that reaches it without a link. A CLAUDE.md or an agent that is also linked into a rules folder keeps its kind and its id, whatever the order of the roots. Only a file that every root reaches through a link takes the kind of its first hit.
- A path with a tab, a line break or a backslash in it enters no table: not as a root, not as a file's name, not as a folder above a root, not as the real path a link leads to. Every table the runner keeps is one path to a line beside tab-separated facts, `@tsv` doubles a backslash and `shasum` rewrites a line that holds one, so such a path would be staged or fingerprinted wrongly. It is passed over and named. The shared expansion passes it over too, so the hook and the full check agree, and the walk of a rules folder also names a folder it cannot read.

- Above every group folder and repo the audit looks in each folder, up to the top of the disk, for `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md` and the rule files under `.claude/rules`. A session loads all four from there, seen on 2.1.296 through the `InstructionsLoaded` hook, where the documentation names only the first two. Skills, agents and commands load only up to a repository's root, so they are not looked for above one.
- A file above the roots is reached by every root beneath it and takes its tier by the rule there is. A root nested inside a repo does not widen that repo's own files, or every such pair would turn the outer repo's CLAUDE.md global. An item with no home names the roots it sits above, as `above`.
- A custom command file is a kind of its own, `command`, judged as a skill is. It is looked for by the type of root, as a rule file is: `commands` in a config folder and `.claude/commands` in every other root, never a repo's own top-level `commands` folder and never above a root. One walk serves both folders, and its notes carry the folder's name so each message names the right one.
- An import is `@path` in a CLAUDE.md, a rule file or an imported file. Claude Code finds one by running the file through a Markdown lexer and looking in the text that comes out, so what counts depends on that lexer's every rule. The program in `lib/imports.sh` follows the lexer's block rules, which were worked out from what Claude Code 2.1.296 loads: frontmatter, lists, quotes, fences, indented code, HTML blocks, link definitions and both kinds of heading. A reader of lines could not be made safe, as three reviews showed.
- Following an import no session loads would send the model a file it should never see, so the program follows one only where it is sure. Inside a paragraph it stops at the first place a code span, a tag or a link could hide what follows, and reads on in the next block. Where it cannot follow the lexer at all it sets `lost` and reads nothing more from the file: a lazy line after a list or a quote inside a quote, which the lexer handles by lengths the program does not keep; an attribute split by white space that is not a space; a title that runs past two hundred lines; and one of the three bytes the program uses as stand-ins. Nesting past sixty blocks drops everything the file named, since Claude Code drops a file whose nesting overflows its lexer.
- The text of a list item is an exception both ways. Claude Code looks in it before any span or link is taken out, so an import inside a code span there loads, and the program follows it. The lexer goes on treating what follows a nested list in an item as a paragraph, and the program keeps that flag as the lexer does.
- Frontmatter ends at the first three dashes anywhere after its first line, and the white space after them goes with it, so a body's first line loses its indentation. A path counts only when it starts with a letter, a digit, a dot, a dash, an underscore, `./`, `~/` or `/`.
- `test/import-forms.json` records 1,013 forms with what Claude Code 2.1.296 did with each, seen through the `InstructionsLoaded` hook, and what the program does: it follows 443 of the 525 Claude Code loads and none of the rest. The runner suite pins the program's side and the loading check holds it to Claude Code. A form may name its own file with `ref` and `file`, or put it beside the rule file with `beside`. What the program misses is in `docs/limits.md`, under the imports it cannot be sure of.
- Only the file types Claude Code imports are followed: a file with no extension, or with one of the 78 in `IMPORT_EXTENSIONS`, in either case. Any other is named on stderr and never staged, because the audit must not send the model a file no session would load.
- An imported file is an item of kind `import`, unless discovery finds it by itself, and then it keeps its kind and its id. Every root that reaches a file reaches what it imports, four files deep. Home still decides who reads it: a group's notes imported by the global CLAUDE.md are read under that group's account and judged as global. It is judged line by line and never for being too generic, since it may be a README.
- The hook cannot read files, so it learns of imports from the baseline, which marks every path an import named, whether or not it named a file. The hook stats those with the rest: one that had a file and has none is gone, one that named nothing and now resolves counts as a dangling link's does, and one that was a folder or a file left out, and is now a file of another identity, counts too. A new import changes the file that holds it, which is counted already. The full check puts a marked path that exists and is no item into `rejected`, so the hook stops counting one that has become a folder.
- An import that leaves its project counts as loaded. Claude Code asks the person once before it loads one, and the files cannot say what was answered.
- The walk upward is part of the shared expansion and starts no process. Discovery resolves a file above the roots once and writes a hit for every root beneath it. `hits.tsv` has seven columns: the sixth says how a hit was made, and the seventh which file imported it.

## Still open

- Conditional keywords in `--json-schema` are unverified, which is why the response schema uses structural keywords only.
- A skill is judged by its SKILL.md alone. Its sibling files are not staged.
- `claude plugin details` estimates about 198 always-on tokens for the four skills. It counts every description, while the documentation says a skill with `disable-model-invocation` costs nothing until it is invoked, and a session's own list of skills leaves all four out. So the figure is the estimator's and not a cost.
- Incremental audits are unbuilt. A batch whose files, examples, prompt and model are unchanged could keep its judgements and spend nothing, and the fingerprints are the groundwork. The open question is what the report should say about when each judgement was made.
- A changed sibling of a SKILL.md is not drift, because siblings are not judged.
- Both workflows first ran on 2026-10-14, and both suites passed on a hosted macOS runner. Some cases allow 15 or 20 seconds, so a slower runner could still time one out.
- Skills and agents are still looked for under every root, so a repo's own top-level `skills` and `agents` folders are audited, where its `rules` folder is not.
- `AGENTS.md` is not audited unless something imports it. By default Claude Code reads it only in a repo with no CLAUDE.md of its own.
- A `.claude/rules` folder nested deeper inside a repo is not audited, as a nested CLAUDE.md is not.
- The cap on a rules folder bounds depth and not width. Several links inside one rules folder that point back into it multiply the found paths: one gives ten, two give about five hundred and three about ten thousand. A link from a rules folder to a large tree is walked eight folders deep at every quick check. Claude Code itself detects a circular link; remembering each folder's real path as it is walked would do the same here, with `cd -P` and no process.
- A file that could not be read at the audit and can be now is not drift to the hook, whether a pattern found it or an import named it: making it readable changes neither its size nor its time.
- The import program is held to the lexer inside Claude Code 2.1.296. A later version may read Markdown differently, and only the loading check will show it.
- Reach follows import edges until nothing changes, so a file can be given a root it has only through a chain longer than four.
- A file above a repo and a second repo nested in the first, outside every root, is judged as global, because the two roots count as two owners.

- Test first at the seam: add the smoke case, watch it fail, then change the code.
- The stand-in `claude` takes its modes from a file beside it, `fake.env`, which `fake_settings` writes from `EXTRA_ENV` before every run. The judge's session is given a named list of variables, so nothing set in the environment reaches the stand-in there.

- The hook is tested by running the command that `hooks/hooks.json` declares, with the stdin and the environment Claude Code sends. `clock_forward` puts a stand-in `date` first on `PATH` to move the clock, and `log_calls` does the same for any program whose calls a case wants to count.
- To see the reminder for real, start `claude --plugin-dir .` in a trusted folder with `CUSTODIAN_HOME` pointing at a fixture data folder whose estate has drifted. A headless session will not show it, by design.
- `test/run.smoke.sh --loaded` is the loading check. It starts the real `claude`, logged out, in every group folder and repo of an invented estate whose global root is the session's config folder, has Claude Code's own `InstructionsLoaded` hook record what each session loads, and compares that with the dry run. It stops before comparing if a session is not refused for want of a login, so it costs nothing. Run it after a Claude Code update and after changing discovery or `lib/imports.sh`.
- `test/run.smoke.sh --live` is the taste check. It calls the real model against an invented estate, judging with the owner's own examples when they are filled in. It spends usage and may wobble. Run it after changing `lib/prompt.md`.
- To look at the page, generate it from a fixture data folder and open the file. Check the console for policy errors, then the narrow layout and the dark appearance.
- `claude --plugin-dir .` loads the plugin for one session. `claude plugin validate --strict .` must pass.
- Traps that have already bitten:
  - an empty array under `set -u` needs `${a[@]+"${a[@]}"}` in bash 3.2;
  - bash 3.2 brace-expands JSON inside nested quotes in a command substitution, so build JSON with `jq` and pass it in a variable;
  - macOS temp paths resolve from `/var` to `/private/var`, so roots and hits are compared by canonical path;
  - a glob cannot see through a dangling folder link, which is why dangling containers are reported separately;
  - glob characters in a path have to be escaped before `compgen -G`, which the config's own globs still go through; the patterns under a root are matched by the shell's own globbing with the root quoted;
  - a watchdog left running after the runner dies would later signal a recycled pid, so cleanup kills it;
  - `jq -R` fed several files joins a last line that has no newline onto the next file's first line, so staged files are read one at a time;
  - `cut | grep -q` under `pipefail` reports failure when `grep` exits early on a long input, so membership checks use one `awk`;
  - `die` inside a pipeline or a process substitution only leaves that subshell, so render to a file, check the status, then move it into place;
  - the status of a `while ... done < <(...)` loop says nothing about the command feeding it;
  - inside a function bash 3.2 keeps every process substitution open until the function returns, and past about 250 of them a command substitution comes back empty or the shell spins at full CPU, so a loop inside a function reads from a file in the work directory;
  - the smoke suites must never read the owner's own examples or config;
  - a local-path plugin install copies untracked and ignored files too, so keep nothing private in the working tree;
  - a strict plugin validation rejects a CLAUDE.md at the plugin root, so the maintainer's pointer lives in `.claude/`;
  - a patch that drops one closing quote flips the quoting of the rest of a bash file, `bash -n` still passes, and text inside test strings starts to execute. A suite that hangs on `sed` reading stdin is this;
  - a temp file made outside the caller's work directory survives the caller's trap, so helpers take the work directory as an argument;
  - `jq`'s `.remind // true` turns a false into true, so a boolean with a default is read with `has`;
  - `compgen -G` reports no match as a failure, which `pipefail` passes on to the whole expansion;
  - a `read` given fewer names than a row has columns puts the rest of the row in the last name, so a new column in the roots table means naming it in every `read` of that table;
  - in bash 3.2 a `$'\n'` inside a double-quoted parameter expansion is not a newline, so the newline goes in a variable first;
  - `$!` after `cd x && a | b &` is the subshell and not `b`, so a test that must kill a process has the process write its own pid;
  - a deleted file is both a missing found path and a missing judged file, and counting both reports one change as two;
  - BSD `stat -L` describes the link itself when it cannot follow it, so a dangling link looks resolved unless the file type is asked for too;
  - a root written with a trailing slash made two readings of one path, and everything under it was then rejected as unknown, so the config's roots are read in one function only;
  - one `awk` per suspect file is one process per file as soon as a checkout touches everything, so the cost case touches everything;
  - a process killed between forking and exec'ing leaves a child that still runs whatever is first on its `PATH`, so a test that swaps a stand-in after a kill counts in a second folder;
  - copying the rest of a line once for every at sign or backtick in it is quadratic, and a manifest on one line took a minute, so the import program splits a line once and walks the pieces;
  - this awk splits on one character in linear time and on a pattern in quadratic time, and on one character it also splits at every line break, so the import program joins a paragraph's lines with a byte of its own before it splits;
  - a guess at how Claude Code reads Markdown is not a fact until a logged-out session has been asked: of the import program's rules, each one written from reasoning alone was wrong somewhere, and random documents found what written cases did not;
  - an import's path runs to the next white space, so a comma or a full stop straight after `@path` makes it name nothing, in a fixture as in a real file;
  - a rename can collide with a local of the same name inside one function, where some assertions then fail and others pass without looking, so run both full suites after any rename.
